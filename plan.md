# TrustGraph — Implementation Plan (v2)

> v1 is preserved at commit `0bfdbd7`. This revision keeps v1's core product intact and changes
> five things: a Day 0 is added, dev scale drops 10x, orchestration and Unity Catalog move to the
> front, point-in-time correctness and the decision policy become first-class deliverables, and the
> fraud-investigator agent is promoted from optional stretch goal to a core Day 7 deliverable.

## Project Goal

Build a Databricks-based **fraud detection + merchant trust platform** that combines:

- Transaction fraud scoring
- Merchant trust scoring
- Streaming / velocity features
- Customer–merchant–device–IP–bank relationship graphs
- Fraud-ring detection
- Delayed fraud / chargeback labels
- MLflow model tracking and a per-scenario evaluation harness
- A decision policy layer derived from a cost matrix
- Risk analytics dashboard
- An AI fraud-investigator agent with an automated verification gate

The goal is **not** a production payment network. The goal is a convincing end-to-end prototype
that demonstrates the architecture, the product idea, and — equally — the engineering discipline
around correctness: no label leakage, no over-claimed numbers, every risk decision explainable.

## Positioning note

This is a **solo, one-week prototype on synthetic data**. Describe it that way everywhere. The
credibility of the project comes from the rigor (point-in-time correctness, per-scenario eval,
cost-derived thresholds, verified agent output), not from claimed scale or accuracy.

## Provenance

TrustGraph is a **new, independent project**, not a rebuild of anything. The earlier TrustPulse
hackathon entry is not retrievable or modifiable, so no code, data, design document, or diagram
from it — or from any employer — is carried over here. Everything in this repository is written
from scratch against synthetic data generated by `src/simulation`.

State this plainly whenever the project comes up. Someone currently working in payments showing a
fraud-detection portfolio project will be asked, and the answer is short and clean: independent
project, synthetic data, no employer code or data, domain familiarity only.

Corollary: because this is a new project rather than a re-implementation, it carries no obligation
to the original TrustPulse thesis (agent identity and trust attestation). That idea remains
unbuilt and is worth revisiting separately — it is more differentiated than merchant fraud
scoring, which is a well-populated demo genre.

# 0. Environment Strategy

## Two environments, one codebase

| | Build environment | Proof environment |
|---|---|---|
| Where | Databricks **Free Edition** | Databricks **trial** (own cloud account) |
| When | Day 0 – Day 7 | A separate 1–2 day window, *after* Day 7 |
| Scale profile | `dev` (and `demo` for the recorded walkthrough) | `proof` |
| Purpose | Build and iterate on all logic | Scale and performance experiments only |

**The trial clock is a burning fuse.** It starts when the trial is created, not when it is first
used. Do not create it until the code is finished, parameterized, and runs green end to end on
Free Edition. On a trial, Databricks waives DBUs but the underlying cloud compute bills to your own
account — set a budget alarm before the first `proof` run, and do not start the clock during an
interview week.

## Consequences of Free Edition being serverless-only

These are decided now, not discovered on Day 4:

- **No GraphFrames.** Serverless does not accept JVM cluster libraries. Connected components will
  be computed either by iterative label propagation in Spark SQL, or by pulling the edge set to the
  driver and using `networkx` / `igraph`. At `dev` entity counts the driver-side route is
  legitimate — state that choice explicitly in `docs/architecture.md` rather than leaving a reader
  to assume a failed attempt at distribution.
- **No Photon toggle.** Serverless is always Photon, so "Photon on/off" is not an available
  performance lever. The tuning story is liquid clustering, file sizing and compaction, join
  strategy and broadcast thresholds, Auto Loader batch sizing, and cost per run.
- **No `spark.sparkContext` / RDD API** under Spark Connect. Synthetic data generators reach for
  `sc.parallelize` by reflex — use `spark.range()` and `spark.createDataFrame` throughout.
- **Capacity limits are real**, which is why the `dev` scale profile is 10x smaller than v1.
- **Model Serving and online feature tables may be unavailable.** The planned fallback is batch
  scoring into a Delta table. The demo reads identically; "real-time" was already a stretch goal.

## Everything is config-driven

No catalog name, row count, threshold, or weight is ever hardcoded. This is what makes the move
from Free Edition to trial a 20-minute change instead of a lost day.

# 4. Fraud Scenarios

Do not assign fraud randomly. Generate fraud through behavioral scenarios.

## Scenario A — Account Takeover
```text
existing customer + new device + new IP/location + high-value txn + unusual merchant
```
Features: `new_device`, `distance_from_previous_txn`, `amount_vs_customer_avg`, `new_country`

## Scenario B — Card Testing
```text
same payment method + many small transactions + many merchants + short time window
```
Features: `payment_txn_count_1m`, `payment_unique_merchants_5m`, `small_payment_velocity`

## Scenario C — Fraud Ring
Groups such as 20 customers / 3 devices / 2 IPs / 4 merchants sharing infrastructure.

Features: `shared_device_count`, `shared_ip_count`, `risky_neighbor_ratio`,
`connected_component_size`, `distance_to_confirmed_fraud`

## Scenario D — Merchant Collusion
Multiple merchants sharing bank account, owner, devices, customer clusters. Elevated chargebacks.

## Scenario E — Bust-Out Merchant
```text
Month 1-3 normal -> Month 4 rapid growth -> Month 5 ticket rises
-> Month 6 risky customers rise -> Month 7 chargebacks spike
```

## Scenario H (held out) — Refund Abuse
Generated by the simulator. **No features are engineered for it and it is excluded from training
scenario analysis.** Its only purpose is the Day 5 generalization test: does the model catch a
fraud pattern it was never designed around? Reporting a mediocre number here is a stronger result
than reporting a good one on the scenarios you built features for.

# 5. Label Policy and Point-in-Time Correctness

**This is the most important section of the plan.** In v1 it was one line on Day 5; the leak
actually happens on Day 4, in the graph features.

## The label

The model does not train on `is_fraud`. It trains on chargeback-confirmed fraud, which:

- arrives 7–45 days after the transaction,
- includes **friendly fraud** (`friendly_fraud_rate`) — chargebacks that are not fraud,
- misses some real fraud (`missed_fraud_rate`) — never charged back.

Training data is therefore restricted to transactions old enough for the chargeback window to have
closed. Anything inside the last `max_delay_days` has an incomplete label and is excluded from
training (it can still be scored).

## The rule

> Every feature value used to score a transaction at time `T` must be computable from data
> observable strictly before `T`.

For chargeback-derived signals, "observable" means `chargebacks.reported_at < T`, **not**
`transactions.event_time < T`. This single distinction is where `risky_neighbor_ratio`,
`distance_to_confirmed_fraud`, `fraud_rate_7d`, `fraud_rate_30d`, and `chargeback_rate_30d` all
leak if written naively.

## The deliverable

`tests/test_leakage.py`, running in CI on every commit:

1. **Timestamp assertion** — for a sample of scored rows, re-derive each feature from a snapshot
   filtered to `< T` and assert the values match the stored feature values.
2. **Future-fraud assertion** — assert no feature changes value when future chargebacks are
   deleted from the source tables.
3. **Shuffle test** — train on shuffled labels; PR-AUC must collapse to base rate. If it doesn't,
   something in the feature set encodes the label.
4. **Column ban** — assert `is_fraud` and `fraud_scenario` appear in no feature table and no
   training frame.

Document the policy in `docs/point-in-time-policy.md`. This document and this test suite are the
single most transferable artifact in the project.

# 6. Merchant Trust Score

0–100, where 0 is extremely risky and 100 is highly trusted.

## Components

**Identity risk:** `merchant_age_days`, `business_verified`, `owner_verified`,
`bank_account_age`, `recent_bank_change`

**Transaction risk:** `fraud_rate_7d`, `fraud_rate_30d`, `chargeback_rate_30d`, `refund_rate`,
`decline_rate`, `volume_growth`, `avg_ticket_change`

**Customer quality:** `risky_customer_ratio`, `new_customer_ratio`, `repeat_customer_rate`,
`avg_customer_risk`

**Behavioral risk:** `volume_zscore`, `avg_ticket_zscore`, `new_customer_spike`,
`country_distribution_shift`

**Network risk:** `shared_bank_bad_merchants`, `shared_owner_bad_merchants`,
`shared_device_bad_merchants`, `risky_neighbor_ratio`, `distance_to_bad_merchant`

## Formula

```text
merchant_risk = sum(trust_weights[c] * component_risk[c] for c in components)
merchant_trust_score = 100 * (1 - merchant_risk)
```

Weights come from `config.trust_weights` — never inlined. State plainly in the writeup that these
are **hand-set priors, not learned**, and that the honest next step is to fit them against
chargeback outcomes once enough labeled history exists. Being explicit about this is worth more
than pretending the weights are principled.

# 7. Decision Policy Layer

## What changed from v1, and why

v1 computed:

```text
final_risk = 0.60 * transaction_fraud_probability
           + 0.25 * merchant_risk
           + 0.15 * network_risk
```

Two defects. First, linearly blending a calibrated probability with two hand-weighted indices does
not yield a probability, so thresholds against it mean nothing. Second, merchant and network
features are already model inputs — blending them again double counts them.

## The replacement

**One model, one probability, one policy layer.**

1. The model consumes merchant trust and network features and emits a single calibrated
   probability `p_fraud`. Calibration is verified with a reliability curve (§8).
2. Thresholds come from a cost matrix, not round numbers:

```text
expected_cost(approve)  = p_fraud * (amount + chargeback_fee_usd)
expected_cost(decline)  = (1 - p_fraud) * cost_false_decline_usd
expected_cost(review)   = review_cost + (residual error after analyst)

decline when expected_cost(approve) > expected_cost(decline)
review  when the two are within a band AND review queue capacity remains
```

3. `review_capacity_per_day` caps the review band — the queue is sized to the analysts who exist,
   which is how real risk operations actually works and is a detail interviewers notice.

Because thresholds are now amount-dependent, a $12 transaction and a $12,000 transaction at the
same probability get different decisions. That is the correct behavior and it demos well.

Keep a `decision_policy_version` column on every decision row so decisions stay reproducible after
the policy changes.

# 8. Evaluation Harness

Promoted to a first-class deliverable. `src/eval/` plus `notebooks/09b_eval_report.py`.

Required outputs, all logged to MLflow:

- **PR-AUC**, precision, recall, false-positive rate. Accuracy is not reported at all.
- **Recall by fraud scenario** — a table, not a scalar. "Card testing 0.91, account takeover 0.44"
  is a far better interview artifact than a single global number.
- **Held-out scenario result** (refund abuse) — generalization beyond engineered features.
- **Calibration / reliability curve** — required, because the entire policy layer depends on
  `p_fraud` meaning what it claims to mean.
- **Fraud dollars captured vs. fraud dollars lost**, and false-decline dollars — the business
  framing of the same confusion matrix.
- **Review queue volume** at the chosen thresholds vs. `review_capacity_per_day`.
- **Feature importance**, with a written note on any feature whose importance looks suspiciously
  high (the usual signature of a leak the tests missed).

Baseline first: logistic regression, then XGBoost/LightGBM. Report both. A tree model that barely
beats logistic regression is a real finding and should be reported as one.

## Day 2 — Inject Fraud and Build the Graph


## Day 3 — Bronze / Silver / Auto Loader / **Orchestration skeleton**

Bronze ingestion via Auto Loader from generated files. Silver with deduplication, schema

```text
transaction_id IS NOT NULL
amount > 0
customer_id IS NOT NULL
merchant_id IS NOT NULL
```

**Then build the full job DAG with stub tasks** — `databricks.yml` (DAB) defining every task from

this project is aimed at. Building the skeleton on Day 3 means orchestration can never get cut.

## Day 6 — Decision Policy + Dashboard + Evidence Bundles

Implement the §7 cost-matrix policy layer, writing to `analytics.risk_decisions` with

Dashboard pages:

- **Risk Operations** — transactions, fraud rate, fraud dollars blocked, high-risk merchants,

## Day 7 — Investigator Agent + Verification Gate + Demo

Promoted from v1's optional stretch. The agent is a **narrative layer over the evidence bundle**,
never a retrieval free-for-all.

**Architecture:**

```text
"Investigate merchant M1847"
        |
        v
  Tool: fetch_evidence_bundle(merchant_id)   <- structured, deterministic
        |
        v
  LLM: compose an analyst-readable summary
        |
        v
  VERIFICATION GATE:
    every numeric claim is parsed and checked against the evidence bundle
    every entity reference is checked to exist
    unverified claims are stripped and logged
        |
        v
  Output: summary + citation of the exact feature rows used
```

The gate matters more than the summary. Because Day 6 already computed the ground truth
deterministically, checking the agent's output is mechanical — which is exactly why the
investigation panel was built first. The fallback is built in: if the agent doesn't come together,
Day 6's deterministic panel already satisfies MVP item 11.

`tests/test_agent_verifier.py` includes adversarial cases: an evidence bundle the agent will be
tempted to over-claim on, and a case with insufficient evidence where the correct output is "not
enough signal to conclude."

Then record the demo (§12) and finish the writeup.

**Done when:** the agent produces a cited summary, the gate demonstrably strips a fabricated claim
in at least one test, and the ten-minute demo runs start to finish.

# 12. Demo Story (10 minutes)

1. A normal merchant — trust score ~91.
2. Simulated suspicious activity: volume spike, new-customer spike, chargebacks rising, shared bank
   account detected.
3. Trust score falls across snapshots.
4. A suspicious transaction arrives; features compute; model emits a calibrated probability.
5. Policy layer applies the cost matrix and returns DECLINE — and shows that the *same* probability
   on a small-amount transaction would have been APPROVE.
6. Investigation panel shows the deterministic evidence.
7. Agent narrates it; the gate's verification log is shown alongside.
8. Close on the per-scenario eval table, including the held-out scenario result — stated as a
   limitation, not hidden.

Step 8 is the differentiator. Most portfolio demos end at step 7 with a good-looking number.

# 14. Scale Proof (trial environment)

**Write the hypotheses before creating the trial.** "Ran it bigger" is not a result.

Each experiment gets a hypothesis, a baseline, an intervention, and a measured outcome, recorded in
`docs/scale-experiments.md`:

**Experiment 1 — graph join bottleneck.** At 100M transactions, hypothesis: the graph feature join
dominates. Baseline runtime and cost, then liquid clustering on `(merchant_id, event_time)` plus
broadcasting the merchant dimension. Measure both.

**Experiment 2 — file sizing.** Small-file overhead in the Auto Loader path at `proof` volume;
compaction / target file size, before and after.

**Experiment 3 — sample representativeness.** Re-run the full eval at `proof` scale and compare
per-scenario recall against `dev`. If they match, the 500K dev sample did not distort the model,
and that is a **data-honesty result** worth more in an interview than a throughput number.

Budget alarm set before Experiment 1. Two days maximum.

# 16. What Not to Do

- Build a custom graph database.
- Build a frontend before the pipeline works.
- Train deep-learning models.
- Generate 1B random transactions.
- Spend two days optimizing model accuracy.
- Add RAG for its own sake — the agent has exactly one tool and one job.
- Over-engineer microservices.
- Add 30 fraud scenarios. Five clean ones plus one held out beats thirty incomplete ones.
- Hardcode a catalog name, a row count, a threshold, or a weight.
- Start the trial before Day 7 is green.

# 17. Success Criteria

- Fraud labels come from behavioral scenarios, not random assignment.
- Labels are delayed and noisy, and training respects the chargeback window.
- No feature reads data from after the scoring timestamp, and a test suite proves it.
- Merchant trust changes dynamically over time.
- Graph relationships materially affect risk.
- The model emits one calibrated probability; the policy layer is separate and cost-derived.
- Per-scenario recall is reported, including a scenario no features were built for.
- Risk decisions are explainable from a structured evidence bundle.
- Agent output is machine-verified against that bundle; unverified claims are stripped.
- The whole pipeline runs as one orchestrated job.
- The demo tells one clear fraud story in ten minutes.

Differentiator:

> Traditional fraud systems score a transaction. TrustGraph scores the transaction, the merchant,
> and the network around them — and can prove that none of those scores saw the future.

# 18. Portfolio Description

## Project Title

**TrustGraph — Fraud & Merchant Trust Intelligence Prototype**

## One-Line Description

A solo one-week prototype on Databricks: a network-aware risk platform combining incremental
transaction fraud detection, merchant trust scoring, graph-based entity risk, point-in-time-correct
feature engineering, MLflow model management, a cost-derived decision policy, and a verified AI
investigation agent — built entirely on synthetic data.

## Resume Bullets

- Prototyped a Databricks fraud-risk platform on synthetic transaction streams spanning customers,
  merchants, devices, IP addresses, payment instruments, and settlement accounts, orchestrated as a
  single Lakeflow job and governed through Unity Catalog.
- Designed a point-in-time-correct feature layer with delayed, noisy chargeback labels, backed by an
  automated leakage test suite (as-of reconstruction, future-label deletion, shuffled-label control)
  running in CI.
- Built merchant trust scoring from transaction quality, behavioral anomalies, customer risk,
  verification signals, and graph-network relationships, with daily snapshots.
- Separated model from policy: a single calibrated fraud probability feeding an amount-aware
  decision layer with thresholds derived from a false-decline / fraud-loss cost matrix and bounded
  by review-queue capacity.
- Built an evaluation harness reporting per-scenario recall, calibration, and generalization to a
  held-out fraud pattern no features were engineered for.
- Added an LLM investigation agent over a deterministic evidence bundle, with a verification gate
  that checks every numeric claim against source feature rows and strips unverified statements.

Every bullet is defensible under questioning and none of them claim production scale, production
users, or a real dataset.
