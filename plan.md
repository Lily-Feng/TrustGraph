# TrustGraph — Implementation Plan (v3)

**Fraud and trust for a payments platform where a growing share of transactions are initiated by
AI agents rather than humans.**

> **Version history.** v1 at commit `0bfdbd7`. v2 restructured the schedule and added correctness
> discipline. **v3 (this)** adopts a Stripe-shaped data contract with a real test-mode capture, and
> promotes the agentic half to co-equal. Full schema lives in `docs/data-contract.md`; this
> document is the decisions and the schedule.

## Provenance

TrustGraph is a **new, independent project**, not a rebuild of anything. The earlier TrustPulse
hackathon entry is not retrievable or modifiable, so no code, data, design document, or diagram
from it — or from any employer — is carried over. Everything here is written from scratch, against
Stripe **test mode** and synthetic data generated by `src/simulation`.

State this plainly whenever the project comes up. Someone working in payments who shows a
fraud-detection portfolio project will be asked, and the answer is short and clean: independent
project, Stripe test mode and synthetic data, no employer code or data, domain familiarity only.

## Positioning

This is a **solo prototype**. Its credibility comes from rigor — a real external data contract, no
label leakage, per-scenario evaluation, cost-derived thresholds, verified agent output — not from
claimed scale, accuracy, or users.

# 0. Where this sits in the agentic payments stack

Against the eight-layer decomposition in `Agentic-payment.jpeg` (mapped in full in
`docs/data-contract.md` §0):

```text
L1  Communication & Discovery ......... out of scope
L2  Identity, Trust & Reputation ...... CONSUMED (attestations) + PARTIALLY BUILT (agent_trust_score)
L3  Mandate, Consent & Policy ......... CONSUMED (mandate scope, revocation)
L4  Offer & Transaction Coordination .. THE DATA CONTRACT (Stripe / ACP-shaped)
L5  Authentication, Risk & Compliance .. ***THIS IS TRUSTGRAPH***
L6  Machine-Speed Payment Protocols ... MODELED AS A CHANNEL, not implemented
L7  Settlement Rails .................. out of scope
L8  Post-Transaction Lifecycle ........ CLOSES THE LABEL LOOP (disputes)
```

**The one-sentence pitch:** *a Layer 5 risk implementation that consumes Layer 2 attestations and
Layer 3 mandates, scores Layer 4 transaction flow, and closes the loop with Layer 8 disputes.*

Naming the layers on either side — and being explicit about the ones deliberately not built — is
the scope-boundary move the story inventory already recommends for the eBay 2 TB work. It buys
credibility for everything inside the boundary.

Protocol names under each layer move fast. The data model is built on the durable concepts —
identity, attestation, mandate, delegation, dispute — not on any one spec's field names. Re-verify
before citing any protocol by name in an interview.

# 1. Environment Strategy

## Three environments

| | Build | Capture | Proof |
|---|---|---|---|
| What | Databricks **Free Edition** | **Stripe test mode** (real API) | Databricks **trial** |
| When | Day 0 – Day 7 | Day 0, half a day | after Day 7, 1–2 days |
| Scale | `dev`, then `demo` | ~200–500 real objects | `proof` |
| Purpose | All logic | Capture the real contract and its quirks | Scale and performance experiments |

**The trial clock is a burning fuse.** It starts on creation, not first use. Do not create it until
the code is finished, parameterized, and green end to end on Free Edition. Databricks waives DBUs
during a trial but the underlying cloud compute bills to your own account — set a budget alarm
before the first `proof` run, and don't start the clock during an interview week.

## Stripe test mode — hard rules

- **Test mode only.** `sk_test_…` keys exclusively. A live key never touches this repo.
- Keys in `.env`, gitignored, and the README says so explicitly.
- **Only Stripe's documented test card numbers.** No real cardholder data, no real PII, ever.
- Everything captured carries `livemode: false`; a Silver expectation asserts it.

## Consequences of Free Edition being serverless-only

Decided now, not discovered on Day 4:

- **No GraphFrames.** Serverless takes no JVM cluster libraries. Connected components will be
  iterative label propagation in Spark SQL, or the edge set pulled to the driver with
  `networkx` / `igraph`. At `dev` scale the driver-side route is legitimate — record the choice in
  `docs/architecture.md` so no reader assumes a failed attempt at distribution.
- **No Photon toggle.** Serverless is always Photon. The tuning story is liquid clustering, file
  sizing, join strategy and broadcast thresholds, Auto Loader batch sizing, and cost per run.
- **No `spark.sparkContext` / RDD API** under Spark Connect. Use `spark.range()` and
  `spark.createDataFrame`; generators reach for `sc.parallelize` by reflex.
- **Capacity limits are real** — hence the `dev` profile being 10× smaller than v1.
- **Model Serving and online feature tables may be unavailable.** Fallback is batch scoring into a
  Delta table. The demo reads identically.

## Everything is config-driven

No catalog name, row count, threshold, or weight is ever hardcoded. This is what makes the move to
the trial a 20-minute change instead of a lost day.

Three structural properties worth naming:

   calibrated probability, one policy layer (§8).

   dashboard's investigation page *is* the agent's ground truth, which is what makes an automated
   verification gate possible at all.
3. **Bronze holds captured and synthetic data indistinguishably.** The pipeline cannot tell them
   apart — that is the point of capturing the contract rather than inventing one.

# 4. Data Model

**Full schema: `docs/data-contract.md`.** Not duplicated here. Summary of what exists:

| Family | Objects |
|---|---|
| Stripe core | `customer`, `payment_intent`, `charge`, `dispute`, `refund`, `payment_method`, `balance_transaction`, `radar.early_fraud_warning` |
| Stripe Connect (merchants) | `account` — `charges_enabled`, `payouts_enabled`, `requirements`, `external_account` |
| Agentic extension | `agent`, `mandate`, `agent_session`, plus agentic context on `payment_intent.metadata` |
| Simulator-only | devices, IPs, entity edges, ground-truth scenario labels |

Three modeling decisions worth remembering under questioning:

- **Connect accounts are the merchant model.** `charges_enabled` / `payouts_enabled` /
  `requirements` *are* verification status. A bust-out merchant ends with payouts paused — a real,
  recognizable outcome rather than an invented flag.
- **Agentic context rides in `payment_intent.metadata`**, not in invented top-level fields, because
  that is how it actually travels today. Silver promotes metadata into typed columns.
- **`initiation_channel`** (`human_initiated` / `agent_delegated` / `agent_to_agent`) covers Layer 6
  without implementing it, and carries the project's sharpest observation: at sub-cent,
  machine-speed volumes, scoring each transaction costs more than the fraud it prevents — so you
  score the **agent and the mandate**, and sample the stream.

# 5. Fraud Scenarios

Fraud is never assigned randomly. It is generated through behavior. Six scenarios plus one held out.

## Classic

**A — Account takeover.** Existing customer + new device + new IP/location + high value + unusual
merchant. *Features:* `new_device`, `distance_from_previous_txn`, `amount_vs_customer_avg`,
`new_country`.

**B — Card testing.** Same payment method, many small charges, many merchants, short window.
*Features:* `pm_txn_count_1m`, `pm_unique_merchants_5m`, `small_payment_velocity`. Kept because it
is cheap and contrasts instructively with agent velocity.

**C — Fraud ring, including merchant collusion.** Clusters sharing devices, IPs, bank accounts, and
owners — v2's separate merchant-collusion scenario is folded in here, since it produced the same
shared-infrastructure graph edges. *Features:* `shared_device_count`, `shared_bank_count`,
`shared_owner_count`, `risky_neighbor_ratio`, `connected_component_size`,
`distance_to_confirmed_fraud`.

**E — Bust-out merchant.** Months of normal behavior, then rapid growth, rising average ticket,
riskier customers, a dispute spike, and finally `payouts_enabled = false`.

## Agentic

**F — Mandate scope violation.** Agent transacts outside delegated scope: over
`max_amount_per_txn`, outside `allowed_merchant_categories`, after `expires_at`, or past
`max_txn_count`. *Features:* `amount_over_mandate_ratio`, `category_in_mandate`,
`mandate_age_vs_expiry`, `mandate_txn_count_used`.

**G — Prompt-injection-induced purchase.** A merchant page injects instructions; the agent buys
what the user never asked for. *Signature:* `user_intent_present = false`, short session, first-time
merchant, purchase early in session. *Features:* `intent_signal_absent`,
`session_duration_to_purchase`, `merchant_first_seen_in_session`, `tool_calls_before_purchase`.

**H — Agent impersonation.** An unattested agent claims a known operator's identity. *Features:*
`attestation_level`, `attestation_expired`, `operator_claim_vs_verified`, `agent_first_seen_days`.

## Held out

**Refund abuse.** Generated by the simulator. **No features engineered for it, excluded from
scenario analysis.** Its only purpose is the Day 5 generalization test. Reporting a mediocre number
here is a stronger result than a good number on scenarios you built features for.

# 6. Label Policy and Point-in-Time Correctness

**The most important section of this plan.** The Stripe dispute object makes it materially stronger
than v2's invented chargeback table.

## The label matures in three states

A dispute is not a label the moment it appears. Its `status` walks
`warning_needs_response` → `needs_response` → `under_review` → `won` / `lost`. So as of any scoring
time `T`, a transaction's label is one of:

```text
unknown      no dispute yet, and inside the dispute window   -> excluded from training
provisional  dispute open, unresolved                        -> excluded from training
final        won or lost                                     -> trainable
```

Training uses **final** labels only, on transactions past both the dispute window and the
resolution window. Everything can still be scored.

## Noise comes from the real object, not from a knob

`dispute.reason` supplies friendly fraud for free: `fraudulent` is fraud; `product_not_received`,
`subscription_canceled`, and `credit_not_processed` mostly are not. Combined with configured
`missed_fraud_rate` (fraud never disputed), the label is realistically dirty without inventing
dirtiness.

## The rule

> Every feature value used to score a transaction at time `T` must be computable from data
> observable strictly before `T`.

For dispute-derived signals, "observable" means `dispute.created < T` — and for *resolved* outcomes,
`resolution_time < T`. **Not** `charge.created < T`. This single distinction is where
`risky_neighbor_ratio`, `distance_to_confirmed_fraud`, `dispute_rate_30d`, and every agent- and
merchant-trust component leak if written naively.

## The deliverable

`tests/test_leakage.py`, in CI on every commit:

1. **As-of reconstruction** — re-derive each feature from a snapshot filtered to `< T`; assert it
   matches the stored value.
2. **Future-deletion** — assert no feature changes when future disputes are removed from source.
3. **Label-maturity** — assert no training row has a `provisional` or `unknown` label.
4. **Shuffle control** — train on shuffled labels; PR-AUC must collapse to base rate.
5. **Column ban** — assert simulator ground truth (`is_fraud`, `fraud_scenario`) appears in no
   feature table and no training frame.

Documented in `docs/point-in-time-policy.md`. This document plus this test suite is the single most
transferable artifact in the project.

# 7. Trust Scores

Two scores, one framework, 0–100 where 100 is trusted. Weights come from `config.trust_weights` —
never inlined.

## merchant_trust_score

- **Identity:** account age, `charges_enabled`, `payouts_enabled`, `requirements.currently_due`,
  external account age, recent bank change
- **Transaction:** fraud rate 7d/30d, dispute rate 30d, refund rate, decline rate, volume growth,
  average ticket change
- **Customer quality:** risky customer ratio, new customer ratio, repeat rate, average customer risk
- **Behavioral:** volume z-score, ticket z-score, new-customer spike, country distribution shift
- **Network:** shared bank / owner / device with bad merchants, risky neighbor ratio, distance to
  bad merchant

## agent_trust_score

Reuses the same machinery — cheap, because the framework already exists.

- **Attestation:** `attestation_level`, issuer, expiry state
- **Mandate compliance:** historical scope violations, revocation events, replay attempts
- **Behavioral:** velocity profile vs. channel norm, merchant diversity, session shape
- **Network:** shared devices/IPs with flagged agents, position relative to known-bad clusters
- **Injection:** rate of purchases with `user_intent_present = false`

State plainly in the writeup that both weight sets are **hand-set priors, not learned**, and that
the honest next step is fitting them against dispute outcomes once enough labeled history exists.
Being explicit about this is worth more than pretending the weights are principled.

# 8. Decision Policy Layer

## One model, one probability, one policy

The model consumes merchant trust, agent trust, and network features and emits a single calibrated
probability `p_fraud`, verified with a reliability curve. Trust scores are **not** re-blended
afterward — that was v1's defect and it double-counted features already inside the model.

## Thresholds from a cost matrix, not round numbers

```text
expected_cost(approve) = p_fraud * (amount + dispute_fee_usd)
expected_cost(decline) = (1 - p_fraud) * cost_false_decline_usd
expected_cost(review)  = review_cost + residual error after analyst

decline when expected_cost(approve) > expected_cost(decline)
review  within a band, bounded by review_capacity_per_day
```

Because thresholds are amount-dependent, a $12 and a $12,000 charge at the same probability get
different decisions. Correct behavior, and it demos well.

## STEP_UP — the fourth outcome

For `agent_delegated` transactions there is an option a card network does not have: pause and ask
the human.

```text
STEP_UP when:
    the transaction exceeds mandate.requires_human_confirmation_above, OR
    p_fraud sits in the review band AND a human principal is reachable, OR
    mandate scope is exceeded but agent_trust_score is otherwise high
```

*"The mandate allowed $200, the agent asked for $340, so we didn't decline — we asked the human."*
That is a better demo beat than a binary decline, and it is the diagram's closing line made
operational: **humans set goals, agents execute.**

Every decision row carries `decision_policy_version` so decisions stay reproducible after the
policy changes.

# 9. Evaluation Harness

First-class deliverable. `src/eval/` plus `notebooks/09b_eval_report.py`. All logged to MLflow.

- **PR-AUC**, precision, recall, false-positive rate. Accuracy is never reported.
- **Recall by scenario** — a table, not a scalar. "Card testing 0.91, injected purchase 0.44" is a
  far better artifact than one global number.
- **Recall by `initiation_channel`** — do human-tuned features degrade on agent traffic? This is
  the project's thesis, tested.
- **Held-out scenario result** (refund abuse) — generalization beyond engineered features.
- **Calibration / reliability curve** — required; the whole policy layer depends on `p_fraud`
  meaning what it claims.
- **Comparison against `charge.outcome.risk_score`**, the platform-native baseline: which cases does
  the network-aware model catch that the baseline misses, and what did it cost in false declines?
  A result against a baseline beats a standalone number.
- **Fraud dollars captured vs. lost**, and false-decline dollars.
- **Review and step-up queue volume** vs. `review_capacity_per_day`.
- **Feature importance**, with a written note on anything suspiciously high — the usual signature of
  a leak the tests missed.

Baseline first: logistic regression, then XGBoost/LightGBM. Report both. A tree model that barely
beats logistic regression is a real finding and should be reported as one.

|---|---|
| At-least-once delivery | Dedupe on `event_id`; assert idempotency under replay |
| Out-of-order arrival | Order by `created`, not `ingested_at`; tolerate a missing parent, reconcile later |
| API-version drift | Quarantine unknown shapes to `bronze.stripe_events_rejected`; never fail the batch |
| Integer minor units | Normalize via a currency-exponent table; an expectation asserts no naive `/100` |

Plus metadata promotion (agentic context into typed columns) and expectations:

```text
transaction_id IS NOT NULL | amount > 0 | livemode = false
customer_id IS NOT NULL | created <= current_timestamp()
```

**Then build the full job DAG with stub tasks** — `databricks.yml` defining every task from capture
through analytics refresh, with unwritten stages as no-ops filled in Days 4–7. Orchestration is
named explicitly in the target JD and sat on Day 7 in v1, the most cuttable slot in the week.
Building the skeleton now means it can never get cut.

**Done when:** new files in the Volume flow to Silver automatically, replaying the same file changes
nothing, `databricks bundle validate` passes, and the job runs end to end with stubs.

## Day 7 — Investigator Agent, Verification Gate, Demo

The agent is a **narrative layer over the evidence bundle**, never a retrieval free-for-all.

```text
"Investigate agent A-3391"
        |
        v
  Tool: fetch_evidence_bundle(entity_id)      <- structured, deterministic
        |
        v
  LLM: compose an analyst-readable summary
        |
        v
  VERIFICATION GATE:
    parse every numeric claim, check against the evidence bundle
    check every entity reference exists
    strip and log unverified claims
        |
        v
  Output: summary + citation of the exact feature rows used
```

The gate matters more than the summary. Because Day 6 computed ground truth deterministically,
checking the agent is mechanical — which is exactly why the investigation panel was built first.
The fallback is structural: if the agent doesn't come together, Day 6's panel already satisfies
MVP item 12.

`tests/test_agent_verifier.py` includes adversarial cases: a bundle the agent will be tempted to
over-claim on, and an insufficient-evidence case where the correct output is *"not enough signal to
conclude."*

Then record the demo (§13) and finish the writeup.

**Done when:** the agent produces a cited summary, the gate demonstrably strips a fabricated claim
in at least one test, and the ten-minute demo runs start to finish.

# 13. Demo Story (10 minutes)

1. Real Stripe test-mode events and synthetic volume land in the same Bronze table. Show a replayed
   duplicate changing nothing, and an out-of-order dispute reconciling.
2. A normal merchant at trust ~91; a well-attested agent at trust ~88.

# 17. What Not to Do

- Use a live Stripe key. Test mode only, always.
- Put real card numbers or real PII anywhere near this repo.
- Try to create 500K objects through the Stripe API — capture the contract, synthesize the volume.
- Build a custom graph database.
- Build a frontend before the pipeline works.
- Train deep-learning models.
- Spend two days optimizing model accuracy.
- Add RAG for its own sake — the agent has one tool and one job.
- Add more scenarios. Six plus one held out beats thirty incomplete ones.
- Hardcode a catalog name, row count, threshold, or weight.
- Start the trial before Day 7 is green.

# 18. Success Criteria

- The data contract is real, captured from a live API, and the contract doc matches what arrived.
- Bronze holds captured and synthetic data indistinguishably; Silver handles all four delivery
  quirks, each proven by a test.
- Fraud comes from behavioral scenarios, never random assignment — half of them agent-native.
- Labels mature through three states; training uses final labels only.
- No feature reads data from after the scoring timestamp, and a test suite proves it.
- Merchant and agent trust both move dynamically over time.
- Graph relationships materially affect risk across both entity families.
- One calibrated probability; a separate, cost-derived, amount-aware policy layer.
- STEP_UP exists and fires for mandate-scope cases.
- Per-scenario and per-channel recall reported, including a scenario no features were built for,
  and compared against a platform-native baseline score.
- Agent output is machine-verified against a deterministic evidence bundle.
- The whole pipeline runs as one orchestrated job.
- The demo tells one clear story in ten minutes.

Differentiator:

> Traditional fraud systems score a transaction. TrustGraph scores the transaction, the merchant,
> **the agent, and the mandate it was acting under** — and can prove none of those scores saw the
> future.

# 19. Portfolio Description

## Title

**TrustGraph — Risk and Trust for Agent-Initiated Payments**

## One-line

A solo prototype on Databricks: the risk layer for a payments platform where a growing share of
transactions are initiated by AI agents — Stripe-shaped ingestion captured from a live test-mode
API, point-in-time-correct features over maturing dispute labels, merchant and agent trust scoring,
graph-based network risk, a cost-derived decision policy with human step-up, and an LLM
investigation agent whose every claim is machine-verified.

## Resume bullets

- Prototyped the Layer 5 risk component of an agentic-payments stack on Databricks — consuming
  agent attestations and delegated mandates, scoring Stripe-shaped transaction flow, and closing
  the label loop with disputes — orchestrated as a single Lakeflow job and governed through Unity
  Catalog.
- Captured a live third-party API contract (Stripe test mode) and built ingestion that handles its
  real delivery semantics: at-least-once duplicate events, out-of-order arrival, API-version schema
  drift quarantined rather than failed, and integer minor-unit currency normalization — each
  enforced by a test.
- Designed a point-in-time-correct feature layer over labels that mature through three states,
  backed by an automated leakage suite (as-of reconstruction, future-deletion, label-maturity,
  shuffled-label control) running in CI.
- Built dual trust scoring for merchants and AI agents from transaction quality, behavioral
  anomalies, attestation state, mandate-compliance history, and graph-network position.
- Separated model from policy: one calibrated fraud probability feeding an amount-aware decision
  layer with thresholds derived from a false-decline / fraud-loss cost matrix, bounded by review
  capacity, including a human step-up outcome for transactions exceeding delegated mandate scope.
- Built an evaluation harness reporting recall by fraud scenario and by initiation channel,
  calibration, generalization to a held-out fraud pattern, and comparison against a platform-native
  baseline risk score.
- Added an LLM investigation agent over a deterministic evidence bundle, with a verification gate
  that checks every numeric claim against source feature rows and strips unverified statements.

Every bullet is defensible under questioning. None claims production scale, production users, real
cardholder data, or a real dataset.
